# Kotgent: диспетчер агентских сессий

> **Implementation status (2026-07).** Первый вертикальный срез реализован. `kotgent start` запускает
> **Claude** в `tmux`, закрытие IDE (Detach) оставляет сессию живой, Web UI (`127.0.0.1` + токен)
> продолжает ту же сессию и подсвечивает `needs attention` при approval. Готово: event-sourcing-ядро
> (лог → чистый редьюсер → проекция, restart-safe replay), SQLDelight-хранилище, single-upstream
> `tmux`-fan-out, reconciliation при рестарте daemon, provider-id capture, CLI
> (`daemon`/`install`/`start`/`list`/`attach`/`stop`/`resume`/`interrupt`) и launchd-установка. Пока
> **только Claude** и **только local-only**; Codex, PWA, cloudflared-туннель, Web Push и diff viewer — в
> бэклоге. Как собрать/запустить и что именно вошло — см. [README.md](README.md); паттерны, инварианты и
> гочи тулчейна для дальнейшей работы — [CLAUDE.md](CLAUDE.md). Ниже — исходная концепция (без изменений;
> реализация местами отошла от неё, напр. PTY через POSIX-cinterop вместо `pty4j`, а удалённый доступ —
> cloudflared в бэклоге вместо своего relay).

Проект имеет смысл не как «ещё один терминал», а как local-first диспетчер агентских сессий: процессы живут независимо от интерфейса, а IDE, браузер и телефон становятся взаимозаменяемыми клиентами.

Главное архитектурное решение: `tmux` — транспорт и механизм выживания процесса, но не источник истины.

```text
IDE terminal ───────┐
Desktop Web UI ─────┼──> kotgent daemon ──> tmux ──> Codex / Claude
Mobile PWA ─ relay ─┘          │
                               ├── SQLite: сессии, версии, статусы
                               └── provider adapters: события, approvals
```

Здесь есть два разных вида долговечности:

- Закрылась IDEA или обновился веб-интерфейс — процесс продолжает жить в `tmux`.
- Перезагрузился компьютер — процесс умер, но разговор сохраняется средствами Codex/Claude и восстанавливается через `resume`.

Это важнее, чем пытаться сделать `tmux` бессмертным.

## Модель сессии

В модель сессии стоит заложить:

- агент: Codex или Claude;
- cwd, repository, worktree, branch;
- `tmux` server/session/pane;
- provider session ID;
- понятное имя и теги;
- версию CLI и путь к бинарнику на момент запуска;
- используемую модель;
- состояние: `running`, `needs approval`, `needs answer`, `ready`, `stopped`, `resumable`, `crashed`;
- последнее событие, непрочитанные сообщения и текущий diff.

## Интеграция с агентами

Состояние агента нельзя надёжно определять по тексту терминала. Лучше сделать отдельные адаптеры:

- У Codex есть `app-server` с threads/turns, JSON-RPC-событиями, resume и потоковыми уведомлениями. Но часть интерфейса пока экспериментальная, поэтому её следует спрятать за собственным адаптером и не привязывать доменную модель к конкретной версии протокола. См. [документацию Codex CLI и app-server](https://learn.chatgpt.com/docs/developer-commands?surface=cli#cli-codex-app-server).
- У Claude есть lifecycle hooks, включая события остановки, уведомлений и запросов разрешений; Agent SDK также предоставляет поток событий, ID сессий и resume. См. [Claude hooks](https://code.claude.com/docs/en/hooks) и [Claude sessions](https://code.claude.com/docs/en/agent-sdk/sessions).
- Парсинг ANSI/TUI следует оставить только как fallback. Терминал можно показывать через `xterm.js`, подключая отдельный PTY-клиент к существующему `tmux` pane.

## Интеграция с IDEA

На первом этапе отдельный плагин не нужен. Можно оставить один терминальный таб с командой:

```shell
kotgent attach
```

Внутри будет выбор и переключение между сессиями. Закрытие IDEA отсоединит только tmux-клиент. Позже плагин сможет открывать конкретную сессию, diff или файл, но backend останется тем же.

## MVP

Разумная последовательность разработки:

1. `kotgent start/list/attach/stop/resume`.
2. Отдельный `tmux -L kotgent`, SQLite и восстановление реестра после рестарта daemon.
3. Web UI: вертикальная группировка по проектам, состояния, версия, непрочитанные события.
4. Браузерный терминал с reconnect.
5. Claude/Codex adapters и единая очередь `Needs attention`.
6. PWA, push и diff viewer.

Не стоит начинать с полноценного собственного chat UI. Сначала лучше встроить настоящий TUI в браузер и добавить вокруг него управление сессиями. Rich-rendering сообщений, tool calls и approvals можно постепенно переносить на структурированные протоколы. Git diff при этом можно получать независимо от агента.

## PWA и старый iPhone

Web Push для установленных на Home Screen PWA появился только в iOS/iPadOS 16.4. Если телефон не обновляется хотя бы до 16.4, фоновый push из PWA технически недоступен; останется UI при открытом приложении и запасной канал вроде email, SMS или webhook. См. [требования Apple Web Push](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

Для мобильного доступа не следует выставлять daemon и терминал напрямую в интернет. Безопаснее сделать небольшой relay, к которому Mac подключается исходящим соединением. По умолчанию PWA видит список, статусы и diff; полноценный терминал или shell-input открывается отдельно и с дополнительным подтверждением.

## Возможный стек

Если `kotgent` задуман на Kotlin, естественно выглядят:

- Ktor;
- coroutines;
- SQLite;
- WebSocket;
- `pty4j` для подключения браузерного терминала к `tmux`;
- `xterm.js` на стороне браузера.

Самое неприятное техническое место — PTY и корректная работа нескольких одновременно подключённых клиентов. Остальные части архитектуры сравнительно прямолинейны.

## Основная ценность

Сильная сторона проекта — не оболочка терминала, а единый restart-safe control plane для разных coding agents.

Первый удачный вертикальный срез: запустить Codex или Claude, закрыть IDEA, открыть браузер, продолжить ту же сессию и увидеть, что она требует внимания. Если это работает без шероховатостей, основная ценность продукта уже доказана.
