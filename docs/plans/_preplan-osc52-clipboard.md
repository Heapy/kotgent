# Пре-план — OSC 52: копирование из пейна в буфер обмена браузера

**Статус:** находка + рассуждение. Не план. Следующий шаг — `/planning:make` по этому файлу.

## Находка

**`@xterm/addon-clipboard` — 121 строка, и он есть в 6.0.0.**
`projects/xterm.js/addons/addon-clipboard/src/ClipboardAddon.ts`:

| Строка | Что |
|---|---|
| `:20` | вся активация — `terminal.parser.registerOscHandler(52, …)`; `registerOscHandler` есть в публичном API 6.0.0 |
| `:32` | разбор `<selection>;<base64>`; `?` вместо данных = ЗАПРОС на чтение буфера |
| `:71` | `BrowserClipboardProvider` — `navigator.clipboard.readText/writeText` |
| `:92` | `Base64` с фолбэками на `btoa`/`atob`, если `Uint8Array.toBase64` недоступен |

Провайдер — конструкторный параметр, то есть подменяется без форка.

**Байты, скорее всего, уже доезжают до нашего апстрима.** tmux пересылает OSC 52 клиенту при наличии
`Ms` в terminfo клиента; `Ms` даёт терминальная фича `clipboard`, а она **уже в дефолтных**
`terminal-features` для `xterm*` (`xterm*:clipboard:ccolour:cstyle:focus:title` — прочитано из бинарника
tmux 3.7b). Дефолт `set-clipboard` — `external`: «пытаться установить буфер терминала, но игнорировать
попытки приложений создавать буферы tmux». То есть направление «наружу, к клиенту» включено из коробки.

Если так, то сегодня эти байты доходят до xterm.js и **молча выбрасываются** — обработчика OSC 52 нет.

## Почему это важно

Два сценария, и они разного веса.

**1. Выделение в пейне → системный буфер.** У нас форсирован `mouse on`
(`src/tmux/TmuxOptions.kt:152`), значит drag мышью в пейне — это выделение tmux'а, а не xterm'а. tmux
кладёт выделенное в свой буфер и (при `set-clipboard`) шлёт OSC 52 клиенту. Сегодня цепочка обрывается
на последнем шаге. Сейчас единственный путь скопировать текст из агента — `macOptionClickForcesSelection`
(`resources/webui/components/TerminalPane.js:392`), то есть Alt+drag на macOS, про который надо знать.

**2. Агент сам копирует.** Инструмент внутри агента, который кладёт результат в буфер, работает в
терминале и не работает у нас — асимметрия, которую пользователь замечает не сразу и объяснить себе не
может.

Цена входа несоразмерно мала: один OSC-обработчик и подменённый провайдер.

## Варианты

**A. Вендорить аддон, подменить провайдер на write-only (рекомендую).**
Свой провайдер: `writeText` → наш `writeClipboard` (`resources/webui/lib/clipboard.js`),
`readText` → сразу отклонять. Аддон грузится всегда, статическим относительным импортом из
`TerminalPane.js`.
*Плюс:* минимум кода, чтение буфера закрыто по построению.
*Минус:* +~2 КБ в вендор.

**B. То же, но за device-preference, как unicode-аддоны.**
*Плюс:* операторы, которым это не нужно, ничего не грузят. *Минус:* 2 КБ против 65 КБ у unicode —
причина, по которой там сделан `import()`, здесь не действует; настройка ради 2 КБ только добавит
пункт в диалог. Не рекомендую.

**C. Не вендорить аддон, написать свой обработчик на 20 строк.**
`term.parser.registerOscHandler(52, data => …)` + `atob` + наш `writeClipboard`.
*Плюс:* ноль зависимостей, полный контроль, читается целиком. *Минус:* base64-фолбэки и разбор
selection-параметра придётся написать самим — ровно то, что в аддоне уже есть и протестировано.
**Реальная альтернатива A, решать в плане после того, как посмотрим на diff обоих.**

**Рекомендация: A, с оговоркой — если при вендоринге выяснится, что аддон тянет что-то из `common/`
(он импортирует типы, но проверить сборку ESM-бандла обязательно), переключиться на C.**

## Field-checks перед планом

1. **Доезжает ли OSC 52 до апстрима при дефолтных настройках.** Замер тем же способом, что и в
   пре-плане про 2026 (throwaway сокет + python-pty): в пейне `printf '\033]52;c;aGVsbG8=\a'`, искать
   `\033]52;` в захвате. Если не доезжает — проверить `set -s set-clipboard on`. Это гейт: без него вся
   затея бессмысленна.
2. **Долетает ли выделение мышью.** То же, но через drag в пейне — руками, автоматизировать не стоит.
   Отдельно проверить, шлёт ли tmux OSC 52 при выходе из copy-mode по `y`.
3. **Телефон — самый важный и самый вероятный провал.** `navigator.clipboard.writeText()` без
   пользовательского жеста в iOS Safari, скорее всего, отклоняется, а OSC 52 приходит асинхронно из
   потока, жеста нет по определению. Фолбэк на `document.execCommand("copy")` требует жеста тем более.
   **Если это подтвердится, фича десктопная**, и в описании надо так и написать — не обещать телефон.
   (Плюс на телефоне drag всё равно перехвачен свайп-бриджем: `TerminalPane.js:93`, `:539`.)
4. **Insecure origin.** `navigator.clipboard` недоступен вне secure context. Loopback (`127.0.0.1`)
   secure, публичный хост через cloudflared — HTTPS, тоже secure. Но доступ по LAN-IP по `http://` —
   нет. Проверить, что провайдер в этом случае деградирует тихо, а не сыплет исключениями в консоль на
   каждый OSC 52.

## Безопасность — решается здесь, а не в плане

**Чтение буфера обмена должно быть закрыто.** `ClipboardAddon` на `OSC 52 ; c ; ?` вызывает
`provider.readText()` и отправляет содержимое ОБРАТНО приложению через `terminal.input(…)`
(`ClipboardAddon.ts:27-29`, `:40-52`). Это канал экфильтрации: агент — код, который мы не писали, и он
получил бы содержимое системного буфера пользователя (пароли из менеджера паролей — типичное содержимое).

Наш провайдер обязан отвечать на `readText` отказом. Записать это как инвариант рядом с самим
провайдером, а не в плане: заменить провайдер на дефолтный — однострочная регрессия с непропорциональными
последствиями. Отдельным тестом это не покрыть (JS-харнесса нет), поэтому — комментарий в коде и запись в
AGENTS.md.
